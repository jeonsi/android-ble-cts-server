# 사용성 설계

앱을 만들기 전에 "사용자가 무엇을 보고, 언제 무엇을 눌러야 하는가"를 먼저 정한다.
기준은 하나다: **아이폰에서 설정 > Bluetooth 한 번 탭하고 잊어버리는 경험**을
안드로이드에서도 최대한 그대로 낸다.

## 원칙

1. **한 번 설정하면 잊는다.** 첫 설정 뒤에는 사용자가 앱을 열 일이 없어야 한다.
   매시간 재동기화는 폰이 알아서 응답한다.
2. **안 되면 이유가 보인다.** 이 앱의 실패는 거의 전부 "백그라운드에서 죽었다"이다.
   시계의 소스 아이콘이 반전됐을 때 앱을 열면 *언제까지 살아 있었고 왜 못 받았는지*가
   보여야 한다.
3. **시스템에 맡길 수 있는 건 시스템에.** 페어링 대화상자, 블루투스 켜기, 배터리
   최적화 제외는 앱이 흉내 내지 않고 시스템 화면으로 보낸다.
4. **기기 전용이 아니다.** CTS 솔리시테이션을 광고하는 기기라면 뭐든 목록에 뜬다.
   esp32-c3-clock 얘기는 "힌트"로만 넣는다.

## 사용자 시나리오

| # | 상황 | 사용자가 하는 일 | 앱이 보여 주는 것 |
|---|---|---|---|
| 1 | 최초 설정 | 설치 → 권한 허용 → 기기 광고 켜기 → 목록에서 기기 탭 → 페어링 확인 | 첫 동기화 성공 토스트, 기기 카드에 "방금 동기화" |
| 2 | 평상시 | 없음 | 지속 알림 한 줄: `시간 서버 실행 중 · 마지막 동기화 14:03` |
| 3 | 시계 아이콘이 반전됨 | 앱 열기 | 홈 상단에 원인 배너(블루투스 꺼짐 / 서비스 중지됨 / 65분 넘게 요청 없음) + 로그 |
| 4 | 지금 바로 맞추고 싶음 | 시계 버튼 2~3초(즉시 동기화) | 몇 초 안에 기기 카드가 "연결됨 → 방금 동기화"로 바뀜 |
| 5 | 기기 제거 | 기기 카드 길게 → 제거 | 목록에서 사라짐. 시스템 페어링 해제는 설정 앱으로 안내 |
| 6 | 폰 재부팅 / 블루투스 껐다 켬 | 없음 | 서비스가 스스로 다시 뜸. 알림이 돌아옴 |
| 7 | 폰 교체 | 새 폰에서 1번 반복 | 시계 쪽도 새 본딩이 필요하다는 안내 |

## 화면

화면은 넷이면 충분하다. 탭 바는 두지 않는다.

### 홈 (유일한 진입 화면)

```
┌──────────────────────────────────┐
│ ⚠ 배터리 최적화가 켜져 있습니다     │  ← 상태 배너. 문제 없으면 안 보임
│   1시간마다 오는 요청을 놓칠 수 있음  │     탭하면 해당 시스템 화면으로
│                        [제외하기] │
├──────────────────────────────────┤
│ ● 시간 서버 실행 중                │  ← 서비스 카드. 스위치 하나
│   폰 시간 2026-09-29 14:07 (KST)  │     시각은 실제로 내보낼 값
│                          [  ON ] │
├──────────────────────────────────┤
│ 기기                     [+ 추가] │
│ ┌──────────────────────────────┐ │
│ │ ESP32-C3 Clock               │ │  ← 기기 카드
│ │ 마지막 동기화 14:03 · 대기 중  │ │     상태: 대기 중 / 연결됨 / 오래됨
│ └──────────────────────────────┘ │
│                                  │
│ (기기가 없을 때)                    │
│  아직 등록된 기기가 없습니다.         │
│  기기를 광고 상태로 두고 [추가]를      │
│  누르세요.                          │
└──────────────────────────────────┘
```

- **상태 배너는 우선순위가 있다.** 한 번에 하나만 보여 준다:
  권한 없음 → 블루투스 꺼짐 → 서비스 꺼짐 → 배터리 최적화 → 알림 꺼짐 순.
- **서비스 스위치**가 곧 앱의 전부다. 켜면 foreground service가 뜨고 GATT 서버가
  올라간다. 끄면 알림과 함께 내려간다.
- 기기 카드의 상태 문구
  - `대기 중` — 기기가 광고하기를 기다리는 중(정상. 대부분의 시간이 이 상태)
  - `연결됨` — 지금 붙어 있음(보통 수 초)
  - `마지막 동기화 HH:MM` — 마지막으로 Current Time을 읽어 간 시각
  - `오래됨` — 65분 넘게 읽어 가지 않음. 시계 쪽 아이콘이 반전됐을 시점과 맞춘다
    (esp32-c3-clock의 `SYNC_STALE_MS` = 주기 + 5분)

### 기기 추가 (바텀 시트)

```
┌──────────────────────────────────┐
│ 기기 추가                          │
│ CTS(시간 서비스)를 찾는 기기만 표시    │
│                                  │
│ ◌ 검색 중…                        │
│                                  │
│  ESP32-C3 Clock        -62 dBm   │  ← 탭하면 연결·페어링
│                                  │
│ 기기가 안 보이면                     │
│ · 기기를 광고 상태로 두세요.           │
│ · esp32-c3-clock: 버튼을 2~3초       │
│   눌러 동기화 창을 여세요.            │
└──────────────────────────────────┘
```

- 스캔 필터는 **서비스 솔리시테이션 UUID 0x1805**(`ScanFilter.setServiceSolicitationUuid`,
  API 29+). 주변의 모든 BLE 기기가 아니라 "시간을 달라는 기기"만 뜬다.
- **기기 쪽이 광고 중이어야 한다**는 점이 가장 큰 사용성 함정이다. esp32-c3-clock은
  듀티사이클 때문에 한 시간에 1분만 광고한다. 시트에 힌트를 상시 노출한다.
- 탭 → 서비스를 먼저 올림 → **폰이 `createBond()`로 본딩을 시작** → **시스템 페어링
  대화상자**(Just Works이므로 "페어링" 버튼 하나) → 같은 연결에서 기기가 0x2A2B를 읽음 →
  시트가 닫히고 홈 카드에 "방금 동기화". 페어링 대화상자는 앱이 그리지 않는다.
- 연결만 걸어 두고 기기의 Security Request에 본딩을 맡기면 안 된다. 실기기(2026-09-29)에서
  안드로이드가 키를 끝까지 저장하지 않아 다음 재동기화에 대화상자가 다시 뜨고 실패했다.
  시스템 블루투스 설정에서 먼저 페어링하면 되는데, `createBond()`가 그와 같은 경로다.
- 페어링 대화상자가 안 뜨고 실패하면(기기가 본딩 키를 갖고 있는데 폰은 없는 경우,
  즉 폰 교체) 시트에 "기기 쪽 페어링 정보를 지우고 다시 시도하세요"를 띄운다.

### 기기 상세 / 로그

기기 카드를 탭하면 그 기기의 이벤트 로그가 시간순으로 보인다. 이 화면이 원칙 2를
담당한다.

```
14:03:12  연결됨
14:03:13  Current Time 읽어 감 (2026-09-29 14:03:13 KST)
14:03:15  끊김 (기기가 라디오 끔)
13:03:10  연결됨
…
```

- 남기는 이벤트: 연결 / 읽기 / 끊김(사유) / 서비스 시작·중지 / 블루투스 on·off /
  폰 부팅. "몇 시까지 살아 있었나"를 알려면 서비스 생존 이벤트도 같이 있어야 한다.
- 보관은 최근 7일. 내보내기(공유 시트로 텍스트)를 둔다 — 이슈 리포트용.
- 화면 하단에 `기기 제거` 버튼. 제거는 앱 목록에서만 지우고, 시스템 페어링 해제는
  "블루투스 설정 열기"로 안내한다(앱이 본딩을 풀 수 있는 공개 API가 없다).

### 설정

항목이 적으니 홈 오버플로 메뉴 아래 한 페이지.

- 부팅 시 자동 시작 (기본 켜짐)
- 알림 중요도 안내 — 지속 알림을 조용히 하고 싶으면 알림 채널 설정으로 이동
- 배터리 최적화 제외 상태 + 제조사별 안내 링크(삼성·샤오미 등, dontkillmyapp)
- 로그 내보내기
- 정보: 앱 버전, 서빙 중인 서비스 목록(CTS 0x1805 / Current Time 0x2A2B / Local Time Information 0x2A0F / ANCS 스텁)

## 권한과 시스템 대화상자

첫 실행에서 한 번에 다 묻지 않고, **필요한 순간에 하나씩** 묻는다. 순서와 이유를
사용자에게 한 줄로 보여 준다.

| 순서 | 시점 | 권한 / 대화상자 | 한 줄 설명 | 비고 |
|---|---|---|---|---|
| 1 | 서비스 스위치 ON | `BLUETOOTH_CONNECT` (API 31+) | 기기와 연결하고 시간을 보내기 위해 | GATT 서버 개설에도 필요 |
| 2 | 서비스 스위치 ON | `POST_NOTIFICATIONS` (API 33+) | 실행 중 표시(지속 알림)를 위해 | 거부해도 서비스는 뜸. 알림만 안 보임 |
| 3 | 기기 추가 | `BLUETOOTH_SCAN` (API 31+, `neverForLocation`) | 시간을 찾는 기기를 검색하기 위해 | API 30 이하는 `ACCESS_FINE_LOCATION` |
| 4 | 기기 탭 | 시스템 페어링 대화상자 | (시스템 문구) | 앱이 `createBond()`로 시작, 대화상자는 시스템 것 |
| 5 | 첫 동기화 성공 직후 | 배터리 최적화 제외 (`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`) | 1시간마다 오는 요청을 놓치지 않기 위해 | 성공 경험 뒤에 물어야 수락률이 높음 |

- 최소 SDK는 **API 29**(Android 10)로 잡는다. 솔리시테이션 스캔 필터가 여기서부터다.
- foreground service 타입은 `connectedDevice`. 부팅 브로드캐스트에서 시작할 수 있는
  타입이라 자동 시작이 된다.
- `BLUETOOTH_ADVERTISE`는 필요 없다. 폰은 광고하지 않고, 스캔해서 붙는 central이다.

## 백그라운드 생존이 사용자에게 보이는 방식

README에서 말한 핵심 과제. 기술적으로는 foreground service + 배터리 최적화 제외 +
부팅 자동 시작이고, 사용자에게는 이렇게 보인다.

- **지속 알림 한 줄.** `시간 서버 실행 중 · 마지막 동기화 14:03`. 탭하면 홈.
  액션 버튼은 두지 않는다(실수로 끄는 것을 막기 위해).
- **재연결은 폰이 한다.** 등록된 기기에는 `connectGatt(autoConnect = true)`로
  걸어 둔다. 기기가 한 시간 뒤 광고를 시작하면 블루투스 스택이 스스로 붙는다.
  사용자가 매번 스캔할 일은 없다.
- **죽었을 때의 흔적.** 로그에 마지막 생존 이벤트가 남고, 홈 배너에
  "N시간 전부터 요청이 없습니다"가 뜬다. 이 앱의 첫 버전은 이 흔적으로 어느 폰·어느
  설정에서 죽는지 실측하는 게 목적이다.
- **폰이 없을 때.** 시계 쪽은 1분 창이 닫히면 다음 시간까지 기다린다. 폰이 돌아오면
  다음 창에서 알아서 맞춰진다. 앱은 아무 것도 안 해도 되지만, 기기 카드가 `오래됨`이
  되는 것은 정상 동작이라는 걸 문구로 알려 준다(예: "폰이 근처에 없었을 수 있습니다").

## 시간 데이터 쪽 사용성

- 보내는 값은 **폰의 현지 시간**이다. 홈 서비스 카드에 시간대와 함께 실시간으로
  보여 준다. 시계가 틀리게 나올 때 "폰이 뭘 보냈는지"를 바로 볼 수 있다.
- **Local Time Information(0x2A0F)** 도 같이 서빙한다. 시간대 오프셋과 DST를 담는
  표준 특성이라 기기 쪽이 원하면 쓸 수 있다.
- 폰의 "자동 날짜·시간"이 꺼져 있으면 서비스 카드에 경고를 띄운다. 폰 시간이
  틀리면 시계도 틀린다.
- Current Time의 Adjust Reason 비트는 수동 시간 변경·시간대 변경 시 세팅한다.
  기기가 구독(notify)하면 변경 시점에 알려 줄 수 있지만, esp32-c3-clock은 읽기만 하므로
  첫 버전에서는 notify를 구현하되 UI에는 노출하지 않는다.

## ANCS 스텁: 아이폰용 액세서리가 폰을 아이폰으로 보게 하기

아이폰용으로 설계된 CTS 액세서리는 시간만 읽고 끝나지 않는다. esp32-c3-clock처럼
**ANCS(Apple Notification Center Service)를 탐색해 구독**하는 것이 흔한데, 아이폰에서는
그래야 시스템이 재연결을 관리해 주기 때문이다. 이 앱은 그 서비스를 **껍데기만** 올려
준다.

- 서비스 UUID `7905F431-B5CE-4E99-A40F-4B1E122D00D0` (Apple 사설 UUID, SIG 표준 아님)
- Notification Source 특성(notify) + CCCD 0x2902. 액세서리는 CCCD가 없으면 실패로
  처리하므로 필수
- Control Point(write), Data Source(notify)는 esp32-c3-clock이 안 보지만 다른
  아이폰용 액세서리를 위해 함께 둔다
- CCCD 구독 요청에는 성공 응답만 하고 알림은 하나도 보내지 않는다
- **CTS와 ANCS 스텁의 모든 읽기·쓰기는 암호화된 연결에서만 허용**한다(아이폰과 동일). 암호화
  없이 읽게 두면 기기가 페어링이 끝나기 전에 시간을 읽고 ANCS까지 구독한 뒤 2초 만에 라디오를
  꺼서, 폰의 페어링 대화상자가 링크 끊김으로 사라진다. 실기기(Galaxy S10e, Android 12)에서
  확인한 첫 번째 실패 원인이었다.

**왜 시계를 고치지 않고 이렇게 하는가.** esp32-c3-clock은 "동기화 + ANCS 구독"이 돼야
2초 뒤 라디오를 끄고, 구독이 안 되면 60초까지 켜 둔다. 안드로이드에 ANCS가 없으면
매시간 58초를 낭비한다. 시계 쪽에 "상대에게 ANCS 없음" 상태를 추가해도 되지만, 앱이
아이폰과 구별되지 않게 행동하는 쪽이 README의 목표("아이폰과 동일한 방식")에 맞고,
다른 아이폰용 액세서리에도 그대로 통한다. 시계 코드는 한 줄도 바꾸지 않는다.

**아이폰과 다른 점.** 아이폰에서는 ANCS 구독이 시스템 재연결 관리라는 실제 기능을
한다. 안드로이드에서는 재연결을 앱의 `autoConnect`가 맡으므로 이 서비스는 순전히
상대 기기의 기대를 채워 주는 용도다. UI에는 설정 > 정보의 서비스 목록에만 노출한다.

**확장 여지.** `NotificationListenerService`로 폰 알림을 실제로 흘려보내면 시계에
알림 개수 표시 같은 기능이 된다. 첫 버전 범위는 아니다.

## 결정 사항

- **단일 홈 화면 + 상세**. 탭·드로어 없음. 설정은 오버플로 메뉴.
- **기기 목록은 앱이 관리**한다. 시스템 본딩 목록을 그대로 쓰지 않는다. 같은 폰에
  본딩된 다른 BLE 기기(이어폰 등)가 섞이지 않게 하기 위해서다.
- **여러 기기 동시 지원.** GATT 서버 하나가 모든 연결에 응답한다. 카드만 늘어난다.
- **페어링 UI는 시스템 것**을 쓴다. 앱 안에 PIN 입력 같은 화면을 두지 않는다.
- **최소 SDK API 29.**
- **ANCS 스텁을 GATT 서버에 함께 올린다.** 시계 쪽 코드 변경 없이 매시간 라디오 켜짐 시간을 60초에서 2초로 줄인다.

## 실측 결과 (2026-09-29 ~ 30, Galaxy S10e / Android 12)

- **hourly 재연결은 붙는다.** 앱을 최근 앱에서 스와이프로 닫고 화면을 끈 채 밤새 둔 결과
  23:07부터 06:07까지 매시간 창에서 빠짐없이 연결 → Current Time 읽기 → 2초 뒤 종료가
  기록됐다. 조건은 foreground service + 배터리 최적화 제외뿐이었다. `PendingIntent` 스캔
  같은 추가 장치는 이 폰에서는 필요 없다.
- 스와이프로 닫아도 프로세스와 서비스가 살아 있었다(One UI에서도). 삼성 "절전 앱" 목록에
  들어가는 경우는 아직 못 봤다.
- 시계(ESP32) 재부팅 직후에도 폰이 광고를 보고 바로 붙어 동기화했다.
- **폰 재부팅 뒤 자동 시작.** 처음엔 일반 부팅 신호로 띄웠는데, 이 신호는 잠금 해제 뒤에야 오고
  150여 개 앱 뒤에 줄을 서서 부팅 4분 반 뒤에 서비스가 떴다. 잠금 해제 전 부팅 신호
  (`LOCKED_BOOT_COMPLETED`)로 바꾼 뒤에는 **부팅 25초 만에, 잠금 상태에서** 서비스가 뜨고,
  잠금을 풀기 전에도 시계가 시간을 읽어 갔다. 잠금 해제 전에는 Room과 DataStore를 열 수 없으므로
  서비스 켜짐·자동 시작·기기 목록은 기기 보호 저장소에 사본을 두고(`BootState`), 그 사이의 로그와
  동기화 기록은 메모리에 모았다가 해제 뒤 원래 시각으로 DB에 쓴다.
- 부팅 직후처럼 서비스가 아직 안 떠 있을 때 앱을 열면, 켜 둔 상태라면 화면이 서비스를 바로 띄운다.
- 부수 현상 둘. 동기화는 매번 성공하므로 조치는 선택이다.
  - 절반 정도의 창에서 연결 후 읽기까지 10초가 걸린다. 시계가 암호화 전에 첫 읽기를
    시도해 거부당하고 10초 뒤 재시도하는 경로다(아이폰에서도 같을 것). 시계 쪽에서 거부
    직후 암호화 완료 시점에 바로 다시 읽으면 매시간 10초의 라디오 시간이 줄어든다.
  - 나머지 창에서는 1초 안에 연결·끊김·재연결이 한 번 있고 그 뒤 즉시 읽는다. 원인은
    시계 시리얼 로그로 확인해야 한다.

## 미결 사항

- 삼성 등 제조사 배터리 관리가 foreground service까지 죽이는 경우의 대응은 안내
  링크 이상을 하기 어렵다. 며칠 방치한 뒤 다시 본다.

## ESP32 측 후속 작업 (esp32-c3-clock)

이 앱을 쓰면 시계 쪽에서 드러나는 것들. 별도 리포 이슈로 옮긴다. ANCS linger 문제는
앱의 ANCS 스텁으로 해결하므로 시계 쪽 작업이 아니다(위 절 참고).

- README와 `ble_time.h` 주석의 "아이폰 전용" 문구를 "iOS 또는 이 앱을 깐 안드로이드"로
  갱신.
- 폰 교체 시 시계 쪽 본딩 키를 지우는 조작이 없다. 버튼 조합 하나가 필요할 수 있다.
- 암호화 전 첫 읽기가 거부된 뒤 10초 재시도 대신, 암호화 완료 콜백에서 바로 다시 읽기
  (위 실측 결과 참고). `cts_read_pending`이 걸려 있어 `onAuthenticationComplete`의 읽기가
  건너뛰어지는 것으로 보인다.
